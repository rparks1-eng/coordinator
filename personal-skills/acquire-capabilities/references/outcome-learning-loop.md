# Outcome-learning loop

Use this bounded loop when a prior implementation did not produce the user's observable outcome, or after a run exposes a repeatable workflow inefficiency.

## 1. Rebind the outcome

Write one observable acceptance condition in the user's language. Preserve cost, security, approval, and environment constraints. Do not replace the outcome with a proxy such as “tests passed,” “code committed,” or “endpoint responded.”

## 2. Run the causal gate

Before editing again, list at most four competing causes. For each record:

- supporting and contradicting evidence;
- the cheapest discriminating check;
- what result would falsify it;
- whether the cause is product code, routing, adapter, execution, provider, verification, authority, or stale runtime.

Run the checks with the highest information gain first. If material ambiguity remains, invoke the council in rapid-causal mode. Do not acquire or create a skill until product and stale-runtime causes are separated from procedural gaps.

## 3. Select the intervention layer

- Fix product code for primitives, adapters, state loss, lifecycle, animation, or UI reduction.
- Create or optimize a skill only when reusable procedural knowledge, routing, or verification is missing.
- Acquire an executable only after inventory proves no installed primitive can perform the operation.

## 4. Resume the original task once

Bind the intervention to an immutable candidate and rerun the unchanged acceptance check from clean state. Reject false completion when only a proxy improves. Record rollback and unresolved causes.

## 5. Learn without proliferating skills

At run end, record:

- wrong routing or premature implementation;
- context loaded but unused;
- avoidable tool/agent turns;
- repeated clarification or communication failure;
- verifier that would have caught the issue sooner;
- elapsed time and false-completion outcome.

Choose exactly one response:

1. no durable change for a one-off;
2. add a rejected-pattern note to existing evidence;
3. optimize the existing owning skill after a real failure or three repetitions;
4. create one isolated skill candidate only when no existing skill owns the repeatable workflow;
5. create a product capability task when execution—not instructions—is missing.

Forward-test every skill candidate on at least three motivating tasks plus one held-out neighbor. Promote only measured quality or efficiency improvement with no security, privacy, cost, or false-completion regression.
